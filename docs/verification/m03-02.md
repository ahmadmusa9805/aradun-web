## Implementation and acceptance

- `roles.ts` defines explicit operation grants and deny-by-default behavior. Editor has no CRM or finance grant; Sales cannot publish, reassign ownership, perform sensitive corrections or review audit. Conditional finance has no grant for any role.
- `authorization.server.ts` reloads the current server session and StaffUser for every call. Unknown/revoked/expired sessions, inactive staff and stale accessVersion fail closed. Business operations require trusted stored MFA assurance; primary-only login cannot bypass it. Staff/security changes additionally require both authentication and factor verification within five minutes. There is no factor issuance API here.
- `record-access.server.ts` provides one ownership predicate for reads, counts, search and mutations: assigned inquiry; owned opportunity/contact; Admin business scope. Invalid/guessed/nonowned IDs produce indistinguishable not-found behavior. Feature filters must be allowlisted and conjoined, never overwrite this scope.
- Tasks require both assignment and a matching separately authorized target; task assignment never grants unrelated customer history. Target checks must also be applied before task list counts/pagination/search. Linked contact context projects only ID/display name; it neither grants full contact access nor follows other opportunities/history.
- Own-account targets are self-only, including Admins; a strict safe-field schema rejects roles, status, provider mapping and other privilege fields. No account mutation endpoint or lifecycle implementation is introduced.
- `staff-audit.server.ts` binds the existing audit service's restricted read to a current MFA-verified Admin session, returns its existing minimum DTO and exposes no append method. No audit viewer/HTTP route is activated. Transactional append remains owned by future authorized feature workflows with record checks.

The local M03-02 shared capability criteria are verified. CRM/content/account handlers do not yet exist and are not claimed integrated or end-to-end verified. Each later feature must call current authorization and these record predicates independently of UI/layout guards, enforce field/business evidence gates, check revision and transaction invariants, and test every actual entry point. Role permission alone never authorizes publication, conversion, reassignment or lifecycle changes. No mandatory future integration/test is waived.
