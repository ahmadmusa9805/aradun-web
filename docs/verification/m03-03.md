## Implemented behavior

- Express owns enrollment, verification and account/recovery operations. otplib 13.6.0 performs TOTP generation/verification; Iron 7.0.1 seals seeds with a separate private key. Existing pinned packages are promoted to runtime; library password hashing and the single express-session authority are preserved.
- Enrollment requires a fresh valid primary session, cannot overwrite an enabled or replacement-pending factor, expires after five minutes, and reveals the seed only during setup. Confirmation verifies an exact current TOTP step, atomically fences replay, enables the factor, revokes affected sessions and creates a rotated MFA session. Absolute lifetime is preserved. Database/CAS or response failure cannot grant primary-only access.
- A Store regeneration CAS prevents a previously revoked session from rotating. MFA/account operations still resolve current active staff/accessVersion. Sensitive changes require primary and factor verification within five minutes. Reauthentication uses password sign-in and authenticator verification again; no permanent bypass or silent refresh of absolute/fresh-auth limits.
- My Account requires MFA. It exposes an explicit self-only DTO, allows display name/timezone only, changes password with current password and fresh MFA, and offers recovery pack rotation/logout. Password changes revoke every session, outstanding challenges and recovery packs in the same transaction as the credential update and security event.
- Recovery packs contain ten single-use random 32-byte codes, hashed at rest, with 90-day expiry. Rotation replaces previous codes and revokes other sessions. Raw codes appear once in component memory and can be hidden; never localStorage, URLs, logs or normal fixtures.
- Password plus an unused offline code creates only a five-minute restricted factor-replacement grant and sealed pending seed. Existing sessions and older replacement grants are invalidated. Another unused code can restart an interrupted replacement; the remaining pack is invalidated after successful replacement. Password-only enrollment is blocked while replacement is pending. A verified new TOTP atomically consumes the grant and replaces the factor; the user must sign in again. Recovery material alone never creates business access.
- Password-reset challenges are 32 random bytes, hashed, subject/version/purpose-bound, single-use and 15-minute limited. The library prepares a password hash outside the retryable transaction; challenge consumption, compare-and-set password update, version increment, session revocation and security event commit atomically. Replay, races, expiry, stale mapping/version and rollback are tested.
- **Real email delivery is disabled.** Normal recovery requests return the same truthful acknowledgement for every address and create no undeliverable token. Capture injection requires a marked owned disposable test database, loopback replica-set identity and test runtime. UI never says an email was sent. Real delivery and security-change notifications remain activation gates.
- Four noindex pages: `/staff/verify`, `/staff/recover`, `/staff/reset`, `/dashboard/account`. Forms are POST, accessible and responsive, use existing tokens/components, clear sensitive inputs and preserve safe text on failure. Seeds/grants stay in memory. Runtime rendering prevents build-time API origin capture. No protected account data is prerendered. No marketing analytics or animation added.

All identity mutations retain exact Origin/custom header/strict bounded uncompressed JSON checks. New security POSTs share the explicitly configured identity-login admission budget; no new numeric request allowance selected. New passwords use a documented 15–128 character contract without arbitrary composition rules. Production password policy/rate/proxy review remains required.
